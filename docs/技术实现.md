# AppTraffic 技术实现

AppTraffic 是一个托盘（菜单栏）常驻工具，按应用统计上网流量，并区分直连、经代理、经 VPN 三条路线。本文介绍它用到的技术，以及各部分是怎么配合的。

## 1. 技术栈总览

| 层 | 技术 | 作用 |
|---|---|---|
| 应用框架 | Electron 31 + TypeScript 5 | 托盘程序、弹窗、主进程逻辑 |
| 构建 | electron-vite（Vite 5） | 分别打包主进程、preload、渲染进程 |
| 界面 | React 18 | 弹窗里的统计界面 |
| Windows 流量采集 | Rust（ferrisetw + windows-sys） | 管理员权限的 ETW 助手 `traffic-etw.exe` |
| macOS 流量采集 | 系统自带 `nettop` | 普通权限，按进程、按连接输出字节数 |
| 代理信息 | Clash 兼容 REST API | 每条连接走了哪个节点、目标域名 |
| 打包 | electron-builder | Windows NSIS 安装包；macOS dmg（x64 + arm64） |
| 使用统计 | Umami（自建） | 匿名统计安装数、活跃数，可关闭 |

代码约 3500 行（不含界面），其中 Rust 助手约 800 行。

## 2. 三条路线：直连、经代理、经 VPN

三条路线说的是流量从电脑出去后走了哪条路。

- **直连**：应用直接连目标网站，中间没有任何中转。
- **经代理**：应用把请求交给本机的代理程序（如 Clash Verge 里的 mihomo 内核），由代理替它连目标或转给远端代理服务器。
  - 工作在应用层，按连接、按规则分流：国内网站直连，国外网站走某个节点，同一个应用的不同连接可以走不同的路。
  - 应用要「愿意」把流量交给它，一般通过系统代理设置（HTTP / SOCKS 端口）；不读系统代理的程序不会经过它。Clash 的 TUN 模式例外，它会接管全部流量。
- **经 VPN**：VPN 客户端在系统里建一块虚拟网卡并修改路由，让系统流量进这块网卡，加密封装后经隧道发到 VPN 服务器，再从那里出去。
  - 工作在网络层，对应用透明，应用不需要任何设置。
  - 通常是整机流量或按 IP 段分流，一般没有按域名、按规则的精细分流。

一句话区别：代理是应用把请求交给中间人代办，按连接分流；VPN 是在系统层面把整台电脑的出口换成一条加密隧道。

AppTraffic 也按这个差别判断路线：

| 路线 | 判断依据 |
|---|---|
| 经代理 | 应用连了本机代理内核的端口（回环流量）；再由 Clash API 说明其中哪些连接真的走了代理节点，哪些被规则判为直连 |
| 经 VPN | 应用的流量出现在 VPN 虚拟网卡上（如 Windows 的 WireGuard 网卡、macOS 上有有效地址的 `utun`） |
| 直连 | 走物理网卡（Wi-Fi、有线），且不属于以上两种 |

两个容易混淆的地方：

- **Clash 的 TUN 模式**：技术上和 VPN 一样建虚拟网卡，但本质是代理，靠规则分流。所以 Clash 自己的 TUN 网卡不算 VPN，这部分流量仍按代理统计。
- **VPN 客户端自己的流量**：应用经 VPN 发出的数据，会被 VPN 客户端加密后再从物理网卡发一次，同一份流量出现两次。这部分记为「隧道」，不计入总量。

## 3. 整体结构

```
                  ┌───────────────────────── 主进程（Node.js）─────────────────────────┐
                  │                                                                      │
 traffic-etw.exe ─┼─▶ 系统流量源 ──┐                                                     │
 (命名管道, JSON)  │  (Windows)     │                                                     │
                  │                ├─▶ collector（每秒一次）─▶ merge 对账 ─▶ store 按天记账 ─┼─▶ traffic.json
 nettop ──────────┼─▶ 系统流量源 ──┤                                         │            │
 (标准输出, CSV)   │  (macOS)       │                                         ▼            │
                  │                │                                   快照（IPC）         │
 Clash API ───────┼─▶ 代理流量源 ──┘                                         │            │
 (socket / HTTP)  │                                                          │            │
                  └──────────────────────────────────────────────────────────┼────────────┘
                                                                             ▼
                                                              渲染进程（React 弹窗）
```

主要目录：

- `native/`：Rust 写的 Windows ETW 助手
- `src/main/services/`：与平台无关的核心逻辑（采集调度、对账、存储、代理发现）
- `src/main/platform/`：平台相关部分，`win32/` 和 `darwin/` 各实现一份 `Platform` 接口
- `src/renderer/`：界面
- `src/shared/`：主进程和界面共用的类型与格式化函数

## 4. 系统流量采集

两个平台的采集方式完全不同，但都输出同一种数据结构 `SystemSample`：

- `procs`：每个进程的上网字节数（按网卡拆分）和对端主机
- `loops`：本机回环连接，即「谁连了本机哪个进程的哪个端口」，用来识别「应用 → 本地代理」
- `ifaces`：涉及到的网卡，以及是否判定为 VPN

### 3.1 Windows：ETW + Rust 助手

ETW（Event Tracing for Windows）是 Windows 内核的事件追踪机制，能拿到每个 TCP/UDP 收发事件以及发起它的进程，但需要管理员权限。所以采集放在一个独立的 Rust 程序 `traffic-etw.exe` 里，用 `ferrisetw` 库订阅三个事件源：

| 事件源 | 用途 |
|---|---|
| Microsoft-Windows-Kernel-Network | TCP/UDP 收发事件：进程 ID、字节数、本地和远端地址 |
| Microsoft-Windows-DNS-Client | DNS 查询结果（事件 3008），把 IP 还原成域名 |
| Microsoft-Windows-Kernel-Process | 进程启动事件，记下 exe 路径 |

几个实现要点：

- **进程归属**：用事件里的 PID 字段，不用事件头里的 PID（收包事件的事件头 PID 常常是 4，即 System）。
- **方向**：TCP 事件里 saddr 总是本机、daddr 总是远端，不分收发；UDP 事件则按实际包方向。
- **短命进程**：ETW 事件有约 1 秒的缓冲延迟，进程可能在事件到达前就退出了，事后查不到 exe 路径。所以在进程启动时就把路径记下来。事件里是 `\Device\HarddiskVolume3\...` 这样的 NT 设备路径，用 `QueryDosDeviceW` 转成盘符路径。受保护进程打不开的，退回用 Toolhelp 快照取进程名。
- **回环流量**：目标是 127.0.0.1 / ::1 的连接不算上网流量，用 `GetExtendedTcpTable` 查出监听这个端口的进程，作为一条 `loop` 上报。
- **网卡**：用 `GetAdaptersAddresses` 按本机地址判断流量走的哪块网卡，每 10 秒刷新一次。IfType 为隧道 / 虚拟类型，或名字里带 VPN 相关关键词的，判定为 VPN；Hyper-V、VMware、VirtualBox、蓝牙、WAN Miniport 等排除在外。
- **传输**：每秒把增量序列化成一行 JSON，通过命名管道 `\\.\pipe\apptraffic-etw` 发给托盘程序。管道的安全描述符只允许 SYSTEM、管理员和交互式登录用户访问。托盘程序断开 30 秒后助手自行退出。

**免 UAC 启动**：第一次启用时弹一次 UAC，由 PowerShell 脚本 `etw-task.ps1` 注册计划任务 `\AppTraffic\ETW Collector`，设置为最高权限运行，并授权当前用户启动它。之后每次打开 AppTraffic，用 `schtasks /Run` 静默拉起助手。为了防止权限被滥用，计划任务只会指向 Program Files 下的 `traffic-etw.exe`，这个位置普通用户无法替换文件；装在其他位置时，退回为每次启用都弹 UAC。

### 3.2 macOS：nettop

macOS 自带的 `nettop` 普通权限就能看到所有进程的流量。AppTraffic 常驻一个子进程：

```
nettop -L 0 -s 1 -d -x -n -J interface,state,bytes_in,bytes_out
```

每秒输出一段 CSV：先是进程行（`名字.PID`，以及这一秒的收发字节），下面跟着它当前的每条连接（协议、地址、网卡、状态、字节数）。

几个实现要点：

- **增量**：`-d` 输出差值，但第一段是各进程启动以来的累计值，要丢掉。
- **进程路径**：nettop 里的进程名会被截断到约 15 个字符，所以按 PID 用 `ps -axo pid=,comm=` 查完整路径。遇到不认识的 PID，或者 PID 被复用（进程名对不上）时，重新读一次进程表。
- **回环流量**：`lo0` 上远端端口是另一个进程监听端口的连接，记为 `loop`。监听端口来自 nettop 自己输出的 `Listen` 状态连接。
- **已关闭的连接**：进程行的字节数包括这一秒内已经关掉的连接，但这些连接没有明细行。差额按这个进程上一次可见的连接构成（回环 / 各网卡的比例）分摊。都没有的，记到默认路由网卡上。
- **网卡与 VPN**：用 `ifconfig` 取网卡地址，`route -n get default` 取默认网卡，每 10 秒刷新。有可路由地址的 `utun` / `ppp` / `ipsec` 网卡算 VPN；macOS 自己会挂几个只有 fe80 地址的空闲 utun，这些排除。只连着一个 VPN 服务时，用 `scutil --nc list` 里的服务名作为显示名。地址在 198.18.0.0/15 的是 Clash 的 TUN，不算 VPN。
- **应用名**：macOS 应用常把联网放在子进程里，比如 `Google Chrome Helper`。凡是在 `.app` 包里的进程，都归到包名下。代理内核和 VPN 客户端除外，它们要靠自己的进程名识别。

## 5. 代理信息：Clash 兼容 API

系统流量只知道「这个应用收发了多少字节」，不知道哪些走了代理。mihomo（Clash Meta）、sing-box 等代理内核提供一套 REST API，`/connections` 里列出每条连接的进程、目标域名和代理链路。AppTraffic 每秒轮询一次，按连接 ID 计算差值。

### 4.1 自动发现

用户不用填任何配置，按可信程度依次尝试：

1. **正在运行的内核进程**：按进程名（verge-mihomo、mihomo、clash-meta、sing-box 等）找到内核。从命令行参数里读出配置文件路径（mihomo 的 `-d` / `-f`，sing-box 的 `-c` / `-D`），有时控制接口本身也在命令行上（`-ext-ctl`、`-ext-ctl-pipe`、`-ext-ctl-unix`、`-secret`）。再从配置里读 `external-controller`、`external-controller-pipe` / `-unix`、`secret`；sing-box 读 JSON 里的 `experimental.clash_api`。父进程名用来标出客户端，比如 clash-verge 对应「Clash Verge」。
   - Windows 用 PowerShell 的 `Get-CimInstance Win32_Process` 读进程列表和命令行。
   - macOS 用 `ps`。`ps` 输出的命令行会丢掉引号，路径里有空格时分不清参数边界，所以按「`-参数名 值`」的规律切分。
2. **已知客户端的配置位置**：比如 Clash Verge 的配置目录，用于内核以服务或其他用户身份运行、读不到命令行的情况。
3. **本地 socket 扫描**：Windows 的命名管道 `\\.\pipe\*`，macOS 的 `/tmp`、`/tmp/verge` 下的 `.sock` 文件。

每个候选都用 `GET /version` 确认能连通。连不上时每 10 秒重新发现一次。

### 4.2 连接分类

每条 Clash 连接按进入内核的方式分类，这决定了它和系统流量怎么对账：

| 类别 | 含义 | 系统流量里能看到什么 |
|---|---|---|
| proxy | 应用连本机 HTTP/SOCKS 代理端口 | 应用 → 内核端口的回环流量 |
| tun | 被 TUN 网卡接管 | 应用自己名下的流量 |
| inner | 内核自己发起的（DNS、规则更新等） | 内核名下 |
| gap | 内核总计数里，轮询没捕捉到的短连接 | — |

TUN 模式下还会读 `/configs` 拿到 TUN 网卡名（缓存 30 秒），避免把 Clash 自己的 TUN 网卡当成 VPN。

## 6. 对账（merge.ts）

这是整个项目最核心的部分：系统流量和 Clash 各看到一部分事实，要合成「每个应用、每条路线各多少字节」，而且每个字节只记一次。

**基本原则：系统流量定总量，Clash 定比例。** 系统流量是内核级计数，不会漏；Clash 知道哪些连接走了代理、哪些直连，但轮询有间隔，短连接可能漏掉。

- **Ledger（每个进程两本账）**：一本记应用自己的出网流量，一本记应用经内核端口的流量。系统流量到了就记总量；Clash 的数据可能晚到一两秒，晚到的代理部分用负的「直连」修正，把已经记成直连的字节挪到代理名下。
- **宽限期**：Clash 报了而系统流量一直没看到的字节，等 5 秒再按 Clash 补记，避免两边时间差造成重复。
- **系统代理模式**：应用经代理的量取「应用 → 内核端口」的回环字节；内核自己的出网流量不再算给任何应用，否则会重复。
- **进程识别关闭时**：Clash 的 `find-process-mode: off` 时，代理连接不带进程名。这时把这部分流量按回环流量的比例，分给最近 3 秒内连过内核端口、又没有对应 Clash 连接的本机应用。两边都等对方最多 3 秒。没有这样的应用时，判定为局域网设备经本机代理（allow-lan），记为「未识别」。
- **没有 API 的本地代理**（如 xray）：按各应用连到系统代理端口的回环流量，比例分摊代理进程的出网流量。系统代理端口在 Windows 上读注册表 Internet Settings，在 macOS 上读 `scutil --proxy`。
- **VPN**：流量走 VPN 网卡的，记为「VPN · 网卡名」路线。VPN 客户端进程自己的加密外层流量（内置一份客户端名单，如 openvpn、wireguard、tailscaled 等）记为「隧道」，不计入总量和网速，因为它和应用流量是同一份字节。

对账逻辑有 26 个离线测试场景，覆盖系统代理、TUN、两边时间差、局域网设备、无 API 代理、WireGuard、Clash 和 VPN 同时使用等情况。

## 7. 存储

- 文件：Electron 的 userData 目录下的 `traffic.json`
  - Windows：`%APPDATA%\app-traffic\`
  - macOS：`~/Library/Application Support/app-traffic/`
- 结构：`日期 → 进程 → { 上传, 下载, 各路线字节数, exe 路径, 访问最多的主机 }`。路线是一个 key → 字节数的表：`direct`（直连）、`tunnel`（隧道）、代理客户端名、`VPN · 网卡名`。
- 保留 90 天，内存中累计，每 30 秒和退出时写盘。先写临时文件再重命名，避免写到一半损坏。
- 版本迁移：数据格式从 v1（只有「经 Clash / 直连」）升级到 v2（任意路线）时，自动转换并保留 `.v1.bak` 备份。首次运行会复制前身 ClashTraffic 的历史数据，原文件不动。

## 8. 界面

- 托盘图标常驻，点击弹出无边框窗口，窗口位置按托盘所在的屏幕边缘计算（Windows 任务栏在下，macOS 菜单栏在上）。
- 弹窗始终保持渲染，只是透明并且鼠标穿透，所以每次打开都不闪。渲染进程上报内容高度，主进程据此调整窗口大小。
- 主进程每秒推送一次快照（IPC），包括各数据源的状态、总量、各路线合计、按进程的排行和实时速度。
- macOS 上隐藏 Dock 图标（打包时设置 `LSUIElement`）。托盘左键打开弹窗，右键打开菜单。
- 设置（是否启用系统流量）存在 userData 下的 `settings.json`。

## 9. 匿名使用统计

`analytics.ts` 向自建的 Umami 实例（`umami.wondergarden.top`）上报使用情况，用来了解有多少人在用：

- 事件：首次安装 `app_install`、每次启动 `app_start`、每天一次活跃 `app_active`（应用常驻多天也按自然日计）。
- 内容：随机生成的安装 ID（存在 `settings.json`）、版本号、操作系统、屏幕分辨率、系统语言。**不包含任何流量数据、应用名或主机名。**
- Umami 默认按 IP + UA 识别访客，换网络或升级会被算成新用户。所以上报里的 IP 固定为 127.0.0.1、UA 固定，访客只由安装 ID 决定；代价是没有地区统计。
- 默认开启，可在托盘菜单里关闭；开发版默认不上报（设置 `APPTRAFFIC_ANALYTICS=1` 才上报）。上报失败直接丢弃，不重试。

## 10. 打包与发布

| 平台 | 产物 | 要点 |
|---|---|---|
| Windows | NSIS 安装包（x64） | 安装到 Program Files（perMachine），保证计划任务指向的助手不能被普通用户替换。安装、卸载时先结束助手进程；卸载（非升级）时删除计划任务 |
| macOS | dmg（x64 + arm64） | 没有原生依赖，Intel Mac 上就能打出两个架构。打包后删掉 Electron 框架里中英文以外的语言包，并重新做 ad-hoc 签名（Apple 芯片必须有签名才能运行）。没有开发者证书，第一次打开需要右键「打开」 |

- 两个平台都只保留中文和英文语言包，安装包分别约 72 MB（Windows）、85–93 MB（macOS），大头是 Electron 自带的 Chromium。
- 打包产物按版本号收集到 `dist/<版本号>/`，中间文件放在 `dist/.build/`。

## 11. 设计模式与结构

项目没有刻意套用经典的 GoF 模式，类层次很浅，用的多是轻量的结构手法。整体可以概括为：**端口与适配器架构**；跨平台靠策略、适配器；数据靠观察者、生产者–消费者流转；对账借用会计的冲正分录思路。

下面每种手法都给出：在代码哪里、解决什么问题、代码片段（摘自源码，`// …` 表示省略），算法类的再附伪代码。

### 11.1 端口与适配器（六边形架构）＋ 策略

**问题**：Windows 和 macOS 查进程、读系统代理、采集流量的方式完全不同，但对账、存储、代理发现的逻辑是一样的。

**做法**：核心逻辑只依赖一个接口（端口）`Platform`，每个平台提供一份实现（适配器），启动时按系统选一份（策略）。

```ts
// src/main/platform/types.ts —— 端口：核心逻辑需要操作系统提供什么
export interface Platform {
  listProcesses(names: string[]): Promise<CoreProc[]>;
  knownEndpoints(): Endpoint[];
  socketEndpoints(): Endpoint[];
  systemProxyPorts(): Set<number>;
  createSystemSource(): SystemSource;
}
```

```ts
// src/main/platform/darwin/index.ts —— macOS 适配器
export const darwin: Platform = {
  listProcesses,          // ps
  knownEndpoints,         // Clash Verge 配置目录
  socketEndpoints,        // /tmp 下的 .sock
  systemProxyPorts,       // scutil --proxy
  createSystemSource: () => new NettopSource(),
};
```

```ts
// src/main/platform/index.ts —— 策略选择，全项目只有这一处判断平台
export const platform: Platform = process.platform === 'win32' ? win32 : darwin;
```

核心代码里只出现 `platform.xxx()`，例如 `discovery.ts` 里的 `await platform.listProcesses(CORE_NAMES)`。新增一个平台（比如 Linux），只需要再写一份 `Platform` 实现。

### 11.2 适配器：统一三种上游数据

**问题**：ETW 助手通过命名管道发 JSON，nettop 在标准输出打 CSV，Clash 是 REST API，格式各不相同。

**做法**：每个源实现同一个接口，各自把数据转换成统一的结构，对账只认这两种结构。

```ts
// src/main/services/sources/types.ts
export interface TrafficSource<S> {
  readonly id: string;
  poll(): Promise<S>;   // 取走自上次以来的增量；不可用时抛异常
  reset(): void;        // 出错后丢掉基线
  status(): SourceStatus;
}

export interface SystemSample {
  procs: SysProc[];     // 每个进程的上网字节（按网卡拆分）
  loops: SysLoop[];     // 本机回环：谁连了谁的哪个端口
  ifaces: SysIface[];   // 网卡及是否 VPN
}
```

```
EtwSource    : 管道里的 JSON 行  ──▶ SystemSample
NettopSource : nettop 的 CSV 段  ──▶ SystemSample
ClashSource  : /connections 差值 ──▶ ClashSample
```

### 11.5 生产者–消费者 ＋ 串行队列

**问题**：nettop 按自己的节奏不停输出，collector 每秒来取一次；而且每段数据的处理需要异步查进程路径，处理顺序不能乱。

**做法**：读取端（生产者）只负责累加到缓冲区，`poll()`（消费者）取走后清空；异步处理用一条 Promise 链串起来。

```ts
// src/main/platform/darwin/nettop.ts
private onLine(line: string): void {
  // … 遇到表头说明上一段完整了
  const sample = parseSample(lines);
  // 串行队列：前一段处理完才处理这一段
  this.chain = this.chain.then(() => this.ingest(sample)).catch(() => {});
}

async poll(): Promise<SystemSample> {
  // … 消费：取走累计的增量并清空缓冲
  const sample = { procs: [...this.procs.values()], loops: [...this.loops.values()], ifaces: this.ifaceTable.list() };
  this.procs.clear();
  this.loops.clear();
  return sample;
}
```

collector 侧还加了防重入，慢请求不会让多轮采集叠在一起：

```ts
async function tick(): Promise<void> {
  if (busy) return;
  busy = true;
  try {
    const [c, polled] = await Promise.all([settle(clash), settle(system)]);
    // …
  } finally {
    busy = false;
  }
}
```

### 11.7 账本与冲正分录（对账的核心）

**问题**：系统流量准确但不知道走没走代理；Clash 知道走没走代理，但会晚到一两秒，还可能漏掉短连接。

**做法**：借用会计记账。每个进程一本账：系统流量一到就先按直连记总量；Clash 晚到说明其中有代理流量时，不改已经记下的账，而是追加一笔「负的直连」，把字节挪到代理名下，相当于冲正。

伪代码：

```
class Ledger:
    etw累计, clash累计, clash代理累计, 已记总量, 已记代理

    step(本秒系统流量, 本秒Clash连接):
        etw累计 += 本秒系统流量
        clash累计 += Clash连接的字节
        clash代理累计 += 其中走代理的字节

        目标总量 = etw累计
        if 系统流量已经连续 5 秒没出现:          // 宽限期过了，系统流量看不到这些字节
            目标总量 = max(目标总量, clash累计)    // 按 Clash 补记

        新增 = 目标总量 - 已记总量;  已记总量 = 目标总量

        // 代理比例由 Clash 决定
        目标代理 = 已记总量 × clash代理累计 / clash累计
        代理增量 = 目标代理 - 已记代理;  已记代理 = 目标代理

        return { 新增, 代理增量 }    // 直连 = 新增 - 代理增量，可以是负数（冲正）
```

源码中的关键几行：

```ts
// src/main/services/merge.ts —— Ledger.step()
const booked = this.bookedUp + this.bookedDown;
const clashTotal = this.clashUp + this.clashDown;
const target = this.proxiedByRatio
  ? clashTotal > 0 ? Math.round((booked * this.clashProxied) / clashTotal) : 0
  : Math.min(this.clashProxied, booked);
const proxied = target - this.bookedProxied;   // 可能让本次「直连」为负，即冲正
this.bookedProxied = target;
```

举例：第 1 秒系统流量报 curl 下载 4000 字节，先全记直连；第 2 秒 Clash 报这 4000 字节都走了代理，于是第 2 秒输出「总量 +0、直连 −4000、代理 +4000」。累计结果正确，每个字节只记一次。

### 11.8 缓冲窗口（类似抖动缓冲）

**问题**：两个数据源到达时间不一致，谁先到都可能。

**做法**：用一个很短的等待窗口让两边对齐。项目里有三处：

| 窗口 | 等什么 | 时长 |
|---|---|---|
| `heldSystem` | 代理还在发现中，暂存系统流量，等知道有没有 Clash 再一起对账 | 直到发现结束 |
| Ledger 宽限期 | Clash 报了、系统流量没看到的字节 | 5 秒 |
| `pendingUnknown` / `coreClients` | 未识别进程的代理连接，和最近连过内核的应用互相等 | 3 秒 |

第三个窗口的伪代码：

```
claimUnknownProxy(本秒未识别连接, 本秒经内核的应用):
    所有 coreClients.age += 1
    for 应用 in 本秒经内核的应用（且没有对应的 Clash 连接）:
        coreClients[应用].bytes += 回环字节;  age = 0
    删除 age >= 3 的 coreClients

    待认领 = pendingUnknown + 本秒未识别连接
    if coreClients 为空:
        未识别连接.age += 1
        age >= 3 的 → 记为「未识别进程」（大概率是局域网设备）
        其余继续留在 pendingUnknown
    else:
        按各应用回环字节的比例，把待认领的字节分给 coreClients
        清空 pendingUnknown
```

### 11.9 责任链（降级链）

**问题**：找 Clash 控制接口有多种途径，可信程度不同，而且任何一种都可能失败。

**做法**：按可信程度收集候选，逐个验证，第一个答复的胜出。

```ts
// src/main/services/discovery.ts
export async function discover(): Promise<Discovered | null> {
  const candidates: Endpoint[] = [];
  // … add() 去重后加入
  for (const core of await platform.listProcesses(CORE_NAMES)) add(endpointsFromCore(core)); // 1. 运行中的内核
  add(platform.knownEndpoints());                                                         // 2. 已知客户端配置
  add(platform.socketEndpoints());                                                        // 3. 本地 socket 扫描

  for (const ep of candidates) {
    try {
      const v = await request<{ version?: string }>(ep, '/version', 1500);
      if (typeof v?.version === 'string') return { endpoint: ep, version: v.version };
    } catch {
      // 不是控制接口、密钥不对或没在运行：交给下一个
    }
  }
  return null;
}
```

### 11.10 状态机

`EtwSource` 有几种状态：未启用、等待 UAC、启动中、运行中、出错。状态决定界面显示的文字和按钮。用几个标志位实现，按优先级判断：

```ts
// src/main/platform/win32/etw.ts

  const base = { id: this.id, label: '系统流量' };
  if (this.ready)      return { ...base, state: 'on',    detail: '已启用',                     action: '停用' };
  if (this.prompting)  return { ...base, state: 'off',   detail: '请在管理员授权窗口中确认…', action: null };
  if (this.starting()) return { ...base, state: 'off',   detail: '正在启动…',                 action: null };
```

### 11.11 TTL 缓存与惰性刷新

**问题**：网卡、系统代理这些信息变化很少，每秒执行一次外部命令太浪费。

```ts
// src/main/platform/darwin/sysproxy.ts
const REFRESH_MS = 15_000;
let ports = new Set<number>();
let lastRefresh = 0;

export function systemProxyPorts(): Set<number> {
  if (Date.now() - lastRefresh > REFRESH_MS) refresh();   // 过期才在后台刷新
  return ports;                                           // 立即返回缓存值，不阻塞
}
```

进程路径表则是「未命中才刷新」：nettop 里出现不认识的 PID，或者 PID 被复用（进程名对不上）时，才重新执行一次 `ps`。

## 12. 已知限制

- 只统计 AppTraffic 运行期间的流量。
- 「直连 / 代理」的拆分在 TUN 模式下按 Clash 的比例估算，不是逐字节精确。
- 不在内置名单里的 VPN 客户端，外层流量会和应用流量重复计算。
- Windows 上 WireGuard 内核驱动的外层流量可能记在 System 名下。
- macOS 上 Safari 等 WebKit 应用的流量都记在 `com.apple.WebKit.Networking` 名下，而且只有对端 IP，没有域名（nettop 不提供 DNS 信息）。
- TUN 模式和真实 VPN 场景目前只有离线测试，还没有实机验证。
