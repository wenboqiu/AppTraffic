# AppTraffic 技术实现

AppTraffic 是一个托盘（菜单栏）常驻工具，按应用统计上网流量，并区分直连、经代理、经 VPN 三条路线。本文介绍它用到的技术，以及各部分是怎么配合的。

2.0 起从 Electron 迁移到 Tauri 2：主进程逻辑全部用 Rust 重写，界面（React）基本不变。迁移后 Windows 安装包从约 71 MB 降到 1.5 MB，macOS universal dmg 约 4 MB。

## 1. 技术栈总览

| 层 | 技术 | 作用 |
|---|---|---|
| 应用框架 | Tauri 2（Rust）+ 系统自带 WebView（Windows WebView2、macOS WebKit） | 托盘、弹窗、全部后台逻辑 |
| 构建 | Vite 5 + Cargo | 前端打成静态文件，嵌进 Rust 程序 |
| 界面 | React 18 + TypeScript 5 | 弹窗里的统计界面，通过 Tauri 命令 / 事件和 Rust 通信 |
| Windows 流量采集 | Rust（ferrisetw + windows-sys） | 管理员权限的 ETW 助手 `traffic-etw.exe` |
| macOS 流量采集 | 系统自带 `nettop` | 普通权限，按进程、按连接输出字节数 |
| 代理信息 | Clash 兼容 REST API | 每条连接走了哪个节点、目标域名 |
| 打包 | Tauri bundler | Windows NSIS 安装包；macOS .app / dmg（universal） |
| 使用统计 | Umami（自建） | 匿名统计安装数、活跃数，可关闭 |

Rust 代码约 4500 行（`src-tauri`，含测试），其中 Windows ETW 助手 `native/` 约 800 行。依赖很少：tauri 与它的单实例、自启动插件，serde、ureq（统计上报）、sys-locale，Windows 上再加 windows-sys。

## 2. 三条路线：直连、经代理、经 VPN

三条路线说的是流量从电脑出去后走了哪条路。

- **直连**：应用直接连目标网站，中间没有任何中转。
- **经代理**：应用把请求交给本机的代理程序（如 Clash Verge 里的 mihomo 内核），由代理替它连目标或转给远端代理服务器。
  - 工作在应用层，按连接、按规则分流：国内网站直连，国外网站走某个节点，同一个应用的不同连接可以走不同的路。
  - 应用要「愿意」把流量交给它，一般通过系统代理设置（HTTP / SOCKS 端口）；不读系统代理的程序不会经过它。Clash 的 TUN 模式例外，它会接管全部流量。
- **经 VPN**：VPN 客户端在系统里建一块虚拟网卡并修改路由，让系统流量进这块网卡，加密封装后经隧道发到 VPN 服务器，再从那里出去。
  - 工作在网络层，对应用透明，应用不需要任何设置。
  - 通常是整机流量或按 IP 段分流，一般没有按域名、按规则的精细分流。

一句话区别：代理是应用把请求交给中间人代办，按连接分流；VPN 是在系统层面把整台电脑的出口换成一条加密隧道。

AppTraffic 也按这个差别判断路线：

| 路线 | 判断依据 |
|---|---|
| 经代理 | 应用连了本机代理内核的端口（回环流量）；再由 Clash API 说明其中哪些连接真的走了代理节点，哪些被规则判为直连 |
| 经 VPN | 应用的流量出现在 VPN 虚拟网卡上（如 Windows 的 WireGuard 网卡、macOS 上有有效地址的 `utun`） |
| 直连 | 走物理网卡（Wi-Fi、有线），且不属于以上两种 |

两个容易混淆的地方：

- **Clash 的 TUN 模式**：技术上和 VPN 一样建虚拟网卡，但本质是代理，靠规则分流。所以 Clash 自己的 TUN 网卡不算 VPN，这部分流量仍按代理统计。
- **VPN 客户端自己的流量**：应用经 VPN 发出的数据，会被 VPN 客户端加密后再从物理网卡发一次，同一份流量出现两次。这部分记为「隧道」，不计入总量。

## 3. 整体结构

```
                ┌────────────────────── Rust 主进程（Tauri）──────────────────────┐
                │                                                                    │
 traffic-etw.exe ┼─▶ 系统流量源 ──┐                                                   │
 (命名管道, JSON)│  (Windows)     │                                                   │
                │                ├─▶ collector（每秒一次）─▶ merge 对账 ─▶ store ────┼─▶ traffic.json
 nettop ────────┼─▶ 系统流量源 ──┤                                       │          │
 (标准输出, CSV) │  (macOS)       │                                       ▼          │
                │                │                          快照（emit 事件 / 命令）  │
 Clash API ─────┼─▶ 代理流量源 ──┘                                       │          │
 (socket / HTTP)│                                                        │          │
                └────────────────────────────────────────────────────────┼──────────┘
                                                                         ▼
                                                         WebView（React 弹窗）
```

主要目录：

- `native/`：Rust 写的 Windows ETW 助手（独立的 crate，随安装包分发）
- `src-tauri/src/`：主进程，全部 Rust
  - 与平台无关：`collector.rs`（采集调度）、`merge.rs`（对账）、`store.rs`、`settings.rs`、`clash.rs` / `mihomo.rs` / `discovery.rs` / `controller_config.rs`（代理发现与轮询）、`cores.rs`（内核和 VPN 客户端名单）、`popup.rs`（弹窗窗口）、`analytics.rs`、`types.rs`、`util.rs`
  - `platform/windows/`、`platform/macos/`：平台相关部分，各自导出同一组函数，由 `platform/mod.rs` 按系统选一份
  - `lib.rs`：命令、托盘菜单、启动流程
- `src/renderer/`：界面；`src/renderer/src/api.ts` 是对 Tauri 命令的薄封装
- `src/shared/`：界面用的类型与格式化函数
- `resources/`：托盘图标、`etw-task.ps1`

前后端接口只有几个 Tauri 命令（`get_snapshot`、`source_action`、`show_in_folder`、`open_data_folder`、`close_popup`、`resize_popup`）和一个事件（`snapshot`，弹窗开着时每秒推送一次）。

## 4. 系统流量采集

两个平台的采集方式完全不同，但都输出同一种数据结构 `SystemSample`：

- `procs`：每个进程的上网字节数（按网卡拆分）和对端主机
- `loops`：本机回环连接，即「谁连了本机哪个进程的哪个端口」，用来识别「应用 → 本地代理」
- `ifaces`：涉及到的网卡，以及是否判定为 VPN

### 3.1 Windows：ETW + Rust 助手

ETW（Event Tracing for Windows）是 Windows 内核的事件追踪机制，能拿到每个 TCP/UDP 收发事件以及发起它的进程，但需要管理员权限。所以采集放在一个独立的 Rust 程序 `traffic-etw.exe` 里，用 `ferrisetw` 库订阅三个事件源：

| 事件源 | 用途 |
|---|---|
| Microsoft-Windows-Kernel-Network | TCP/UDP 收发事件：进程 ID、字节数、本地和远端地址 |
| Microsoft-Windows-DNS-Client | DNS 查询结果（事件 3008），把 IP 还原成域名 |
| Microsoft-Windows-Kernel-Process | 进程启动事件，记下 exe 路径 |

几个实现要点：

- **进程归属**：用事件里的 PID 字段，不用事件头里的 PID（收包事件的事件头 PID 常常是 4，即 System）。
- **方向**：TCP 事件里 saddr 总是本机、daddr 总是远端，不分收发；UDP 事件则按实际包方向。
- **短命进程**：ETW 事件有约 1 秒的缓冲延迟，进程可能在事件到达前就退出了，事后查不到 exe 路径。所以在进程启动时就把路径记下来。事件里是 `\Device\HarddiskVolume3\...` 这样的 NT 设备路径，用 `QueryDosDeviceW` 转成盘符路径。受保护进程打不开的，退回用 Toolhelp 快照取进程名。
- **回环流量**：目标是 127.0.0.1 / ::1 的连接不算上网流量，用 `GetExtendedTcpTable` 查出监听这个端口的进程，作为一条 `loop` 上报。
- **网卡**：用 `GetAdaptersAddresses` 按本机地址判断流量走的哪块网卡，每 10 秒刷新一次。IfType 为隧道 / 虚拟类型，或名字里带 VPN 相关关键词的，判定为 VPN；Hyper-V、VMware、VirtualBox、蓝牙、WAN Miniport 等排除在外。
- **传输**：每秒把增量序列化成一行 JSON，通过命名管道 `\\.\pipe\apptraffic-etw` 发给托盘程序。管道的安全描述符只允许 SYSTEM、管理员和交互式登录用户访问。托盘程序断开 30 秒后助手自行退出。

**免 UAC 启动**：第一次启用时弹一次 UAC，由 PowerShell 脚本 `etw-task.ps1` 注册计划任务 `\AppTraffic\ETW Collector`，设置为最高权限运行，并授权当前用户启动它。之后每次打开 AppTraffic，用 `schtasks /Run` 静默拉起助手。为了防止权限被滥用，计划任务只会指向 Program Files 下的 `traffic-etw.exe`，这个位置普通用户无法替换文件；装在其他位置时，退回为每次启用都弹 UAC。

### 3.2 macOS：nettop

macOS 自带的 `nettop` 普通权限就能看到所有进程的流量。AppTraffic 常驻一个子进程：

```
nettop -L 0 -s 1 -d -x -n -J interface,state,bytes_in,bytes_out
```

每秒输出一段 CSV：先是进程行（`名字.PID`，以及这一秒的收发字节），下面跟着它当前的每条连接（协议、地址、网卡、状态、字节数）。

几个实现要点：

- **增量**：`-d` 输出差值，但第一段是各进程启动以来的累计值，要丢掉。
- **进程路径**：nettop 里的进程名会被截断到约 15 个字符，所以按 PID 用 `ps -axo pid=,comm=` 查完整路径。遇到不认识的 PID，或者 PID 被复用（进程名对不上）时，重新读一次进程表。
- **回环流量**：`lo0` 上远端端口是另一个进程监听端口的连接，记为 `loop`。监听端口来自 nettop 自己输出的 `Listen` 状态连接。
- **已关闭的连接**：进程行的字节数包括这一秒内已经关掉的连接，但这些连接没有明细行。差额按这个进程上一次可见的连接构成（回环 / 各网卡的比例）分摊。都没有的，记到默认路由网卡上。
- **网卡与 VPN**：用 `ifconfig` 取网卡地址，`route -n get default` 取默认网卡，每 10 秒刷新。有可路由地址的 `utun` / `ppp` / `ipsec` 网卡算 VPN；macOS 自己会挂几个只有 fe80 地址的空闲 utun，这些排除。只连着一个 VPN 服务时，用 `scutil --nc list` 里的服务名作为显示名。地址在 198.18.0.0/15 的是 Clash 的 TUN，不算 VPN。
- **应用名**：macOS 应用常把联网放在子进程里，比如 `Google Chrome Helper`。凡是在 `.app` 包里的进程，都归到包名下。代理内核和 VPN 客户端除外，它们要靠自己的进程名识别。

## 5. 代理信息：Clash 兼容 API

系统流量只知道「这个应用收发了多少字节」，不知道哪些走了代理。mihomo（Clash Meta）、sing-box 等代理内核提供一套 REST API，`/connections` 里列出每条连接的进程、目标域名和代理链路。AppTraffic 每秒轮询一次，按连接 ID 计算差值。

### 4.1 自动发现

用户不用填任何配置，按可信程度依次尝试：

1. **正在运行的内核进程**：按进程名（verge-mihomo、mihomo、clash-meta、sing-box 等）找到内核。从命令行参数里读出配置文件路径（mihomo 的 `-d` / `-f`，sing-box 的 `-c` / `-D`），有时控制接口本身也在命令行上（`-ext-ctl`、`-ext-ctl-pipe`、`-ext-ctl-unix`、`-secret`）。再从配置里读 `external-controller`、`external-controller-pipe` / `-unix`、`secret`；sing-box 读 JSON 里的 `experimental.clash_api`。父进程名用来标出客户端，比如 clash-verge 对应「Clash Verge」。
   - Windows 用 PowerShell 的 `Get-CimInstance Win32_Process` 读进程列表和命令行。
   - macOS 用 `ps`。`ps` 输出的命令行会丢掉引号，路径里有空格时分不清参数边界，所以按「`-参数名 值`」的规律切分。
2. **已知客户端的配置位置**：比如 Clash Verge 的配置目录，用于内核以服务或其他用户身份运行、读不到命令行的情况。
3. **本地 socket 扫描**：Windows 的命名管道 `\\.\pipe\*`，macOS 的 `/tmp`、`/tmp/verge` 下的 `.sock` 文件。

每个候选都用 `GET /version` 确认能连通。连不上时每 10 秒重新发现一次。

### 4.2 连接分类

每条 Clash 连接按进入内核的方式分类，这决定了它和系统流量怎么对账：

| 类别 | 含义 | 系统流量里能看到什么 |
|---|---|---|
| proxy | 应用连本机 HTTP/SOCKS 代理端口 | 应用 → 内核端口的回环流量 |
| tun | 被 TUN 网卡接管 | 应用自己名下的流量 |
| inner | 内核自己发起的（DNS、规则更新等） | 内核名下 |
| gap | 内核总计数里，轮询没捕捉到的短连接 | — |

TUN 模式下还会读 `/configs` 拿到 TUN 网卡名（缓存 30 秒），避免把 Clash 自己的 TUN 网卡当成 VPN。

## 6. 对账（merge.rs）

这是整个项目最核心的部分：系统流量和 Clash 各看到一部分事实，要合成「每个应用、每条路线各多少字节」，而且每个字节只记一次。

**基本原则：系统流量定总量，Clash 定比例。** 系统流量是内核级计数，不会漏；Clash 知道哪些连接走了代理、哪些直连，但轮询有间隔，短连接可能漏掉。

- **Ledger（每个进程两本账）**：一本记应用自己的出网流量，一本记应用经内核端口的流量。系统流量到了就记总量；Clash 的数据可能晚到一两秒，晚到的代理部分用负的「直连」修正，把已经记成直连的字节挪到代理名下。
- **宽限期**：Clash 报了而系统流量一直没看到的字节，等 5 秒再按 Clash 补记，避免两边时间差造成重复。
- **系统代理模式**：应用经代理的量取「应用 → 内核端口」的回环字节；内核自己的出网流量不再算给任何应用，否则会重复。
- **进程识别关闭时**：Clash 的 `find-process-mode: off` 时，代理连接不带进程名。这时把这部分流量按回环流量的比例，分给最近 3 秒内连过内核端口、又没有对应 Clash 连接的本机应用。两边都等对方最多 3 秒。没有这样的应用时，判定为局域网设备经本机代理（allow-lan），记为「未识别」。
- **没有 API 的本地代理**（如 xray）：按各应用连到系统代理端口的回环流量，比例分摊代理进程的出网流量。系统代理端口在 Windows 上读注册表 Internet Settings，在 macOS 上读 `scutil --proxy`。
- **VPN**：流量走 VPN 网卡的，记为「VPN · 网卡名」路线。VPN 客户端进程自己的加密外层流量（内置一份客户端名单，如 openvpn、wireguard、tailscaled 等）记为「隧道」，不计入总量和网速，因为它和应用流量是同一份字节。

对账逻辑用 Rust 单元测试覆盖（系统代理、无 API 代理共享端口、VPN 路线、TUN 提示等）。Electron 时期的 26 个离线场景脚本没有收入仓库，迁移时按其中最关键的几个重写成测试；TUN 和真实 VPN 场景仍缺实机验证。


## 7. 存储

- 文件：`traffic.json`，放在系统的应用数据目录下的 `app-traffic`（沿用 Electron 版的目录，升级后历史直接接上；环境变量 `APPTRAFFIC_DATA` 可改到别处，测试时用）
  - Windows：`%APPDATA%\app-traffic\`
  - macOS：`~/Library/Application Support/app-traffic/`
- 结构：`日期 → 进程 → { 上传, 下载, 各路线字节数, exe 路径, 访问最多的主机 }`。路线是一个 key → 字节数的表：`direct`（直连）、`tunnel`（隧道）、代理客户端名、`VPN · 网卡名`。
- 保留 90 天，内存中累计，每 30 秒和退出时写盘。先写临时文件再重命名，避免写到一半损坏。
- 版本：数据格式 `version: 2`。读到版本不对或解析失败的文件时，先复制一份 `traffic.json.bad` 再从头开始，不直接覆盖。Electron 时期的 v1 → v2 自动迁移没有移植（1.0 起的数据都已经是 v2）。

## 8. 界面

- 托盘图标常驻。左键切换弹窗，右键菜单：打开、开机自启、匿名使用统计、打开数据目录、退出。托盘悬停提示显示今日总量和实时速度，内容变了才更新。
- 弹窗是启动时建好一次的无边框、透明、置顶、不进任务栏的窗口，之后只做显示 / 隐藏，所以打开是瞬间的，内容高度也已经是上次量好的。失去焦点就隐藏；点托盘图标会先让它失焦隐藏、紧接着才收到点击，所以隐藏后 250 毫秒内的点击不重新弹出。
- 窗口位置以托盘图标为中心，夹在所在屏幕的工作区内；托盘在屏幕下半部（Windows 任务栏）时贴着工作区底部往上长，在上半部（macOS 菜单栏）时贴着顶部往下长。渲染进程上报内容高度（`resize_popup`），Rust 据此调整窗口，贴托盘那一侧不动。
- 弹窗开着时，每秒 `emit` 一次快照事件，包括各数据源的状态、总量、各路线合计、按进程的排行和实时速度；弹窗关着时不推送，空闲开销接近 0。显示时先推一次，打开就有数据。
- 单实例：再次启动程序会唤起已运行实例的弹窗。
- macOS 上设为 Accessory 激活策略（不显示 Dock 图标）。
- 设置（是否启用系统流量等）存在数据目录下的 `settings.json`，字段名与 Electron 版一致。

## 9. 匿名使用统计

`analytics.rs` 用 ureq（native-tls）向自建的 Umami 实例（`umami.wondergarden.top`）上报使用情况，用来了解有多少人在用：

- 事件：首次安装 `app_install`、每次启动 `app_start`、每天一次活跃 `app_active`（应用常驻多天也按自然日计，后台线程每小时检查一次是否换了一天）。
- 内容：随机生成的安装 ID（存在 `settings.json`）、版本号、操作系统、屏幕分辨率、系统语言。**不包含任何流量数据、应用名或主机名。**
- Umami 默认按 IP + UA 识别访客，换网络或升级会被算成新用户。所以上报里的 IP 固定为 127.0.0.1、UA 固定，访客只由安装 ID 决定；代价是没有地区统计。
- 默认开启，可在托盘菜单里关闭；调试版（`debug_assertions`）默认不上报，设置 `APPTRAFFIC_ANALYTICS=1` 才上报。每次上报在独立线程里做，失败直接丢弃，不重试。

## 10. 打包与发布

| 平台 | 产物 | 要点 |
|---|---|---|
| Windows | NSIS 安装包（x64，约 1.5 MB） | 安装到 Program Files（perMachine），保证计划任务指向的助手不能被普通用户替换。`traffic-etw.exe` 和 `etw-task.ps1` 作为资源装在程序旁边。安装、卸载钩子（`installer-hooks.nsh`）先结束助手进程；卸载（非升级）时删除计划任务 |
| macOS | .app / dmg（universal：x86_64 + arm64，约 4 MB） | 没有随包资源（`tauri.macos.conf.json` 把 resources 清空）。没有开发者证书，不签名，第一次打开需要右键「打开」 |

- 程序优化为体积优先：release 配置 `opt-level = "s"`、LTO、strip、`panic = "abort"`。
- 命令：`npm run dist`（Windows，先编译助手再打 NSIS）、`npm run dist:mac`（Mac 上执行）；产物由 `scripts/collect-dist.mjs` 按版本号收集到 `dist/<版本号>/`。
- Mac 上通过 SSH 打包时，Tauri 自带的 dmg 步骤要走 Finder 的 AppleScript，会超时失败；`.app` 已经正常生成，用 `hdiutil create -srcfolder` 手工做 dmg 即可（没有背景图和图标摆位）。
- universal 构建需要 Rust 同时装 `x86_64-apple-darwin` 和 `aarch64-apple-darwin` 两个目标。

## 11. 设计模式与结构

项目没有刻意套用经典的 GoF 模式，类型层次很浅，用的多是轻量的结构手法。整体可以概括为：**端口与适配器架构**；跨平台靠条件编译、trait 适配；数据靠观察者、生产者–消费者流转；对账借用会计的冲正分录思路。

下面每种手法都给出：在代码哪里、解决什么问题、代码片段（摘自源码，`// …` 表示省略），算法类的再附伪代码。

### 11.1 端口与适配器（六边形架构）＋ 编译期策略

**问题**：Windows 和 macOS 查进程、读系统代理、采集流量的方式完全不同，但对账、存储、代理发现的逻辑是一样的。

**做法**：每个平台目录提供同一组函数（端口），`platform/mod.rs` 用 `cfg` 在编译期选一份导出，核心代码只写 `platform::xxx()`。

```rust
// src-tauri/src/platform/mod.rs —— 全项目只有这一处判断平台
#[cfg(windows)]
mod windows;
#[cfg(windows)]
pub use windows::*;

#[cfg(target_os = "macos")]
mod macos;
#[cfg(target_os = "macos")]
pub use macos::*;
```

```rust
// src-tauri/src/platform/macos/mod.rs —— macOS 适配器
pub use processes::{known_endpoints, list_processes, socket_endpoints};   // ps、Clash Verge 配置、/tmp 下的 .sock
pub use sysproxy::system_proxy_ports;                                      // scutil --proxy

pub fn create_system_source() -> Arc<dyn SystemSource> {
    Arc::new(nettop::NettopSource::new())
}
```

核心代码里只出现 `platform::xxx()`，例如 `discovery.rs` 里的 `platform::list_processes(CORE_NAMES)`。和 Electron 版的运行期选择不同，另一个平台的代码根本不会被编译进来，也就没有死代码。新增平台只需要再写一个目录。

### 11.2 适配器：统一上游数据

**问题**：ETW 助手通过命名管道发 JSON，nettop 在标准输出打 CSV，Clash 是 REST API，格式各不相同。

**做法**：每个系统流量源实现同一个 trait，各自把数据转换成统一的结构，对账只认这两种结构。

```rust
// src-tauri/src/types.rs
pub trait SystemSource: Send + Sync {
    fn poll(&self) -> Option<SystemSample>;   // 取走自上次以来的增量；拿不到数据时返回 None
    fn reset(&self);                          // 出错后丢掉基线
    fn status(&self) -> SourceStatus;
    fn auto_start(&self);                     // 启动时：用户之前开过就静默恢复
    fn toggle(&self);                         // 界面上的启用 / 停用按钮
    // …
}

pub struct SystemSample {
    pub procs: Vec<SysProc>,    // 每个进程的上网字节（按网卡拆分）
    pub loops: Vec<SysLoop>,    // 本机回环：谁连了谁的哪个端口
    pub ifaces: Vec<SysIface>,  // 网卡及是否 VPN
}
```

```
EtwSource    : 管道里的 JSON 行  ──▶ SystemSample
NettopSource : nettop 的 CSV 段  ──▶ SystemSample
ClashSource  : /connections 差值 ──▶ ClashSample
```

### 11.5 生产者–消费者

**问题**：nettop 按自己的节奏不停输出，collector 每秒来取一次。

**做法**：读取线程（生产者）解析每段输出、归因后累加到共享缓冲区；`poll()`（消费者）取走后清空。读取线程是单线程顺序处理，所以不需要额外的串行队列；用 `generation` 计数区分新旧读取线程，停止后旧线程发现代数变了就直接退出。

```rust
// src-tauri/src/platform/macos/nettop.rs
fn read_loop(stdout: ChildStdout, gen: u64, inner: &Arc<Mutex<Inner>>, table: &SharedTable) {
    // … 逐行读；遇到表头说明上一段完整了
    let sample = parse_sample(&done);
    ingest(&sample, &mut attributor, &mut paths, inner, table, gen);   // 累加进缓冲区
}

fn poll(&self) -> Option<SystemSample> {
    // … 消费：取走累计的增量并清空缓冲
    let sample = SystemSample { procs: s.procs.values().cloned().collect(), /* … */ };
    s.procs.clear();
    s.loops.clear();
    Some(sample)
}
```

collector 自己是一条每秒一次的后台线程，一轮做完才开始下一轮，所以慢请求不会让多轮采集叠在一起。会拖慢的事（Clash 发现要起 PowerShell、读系统代理要起 `reg` / `scutil`）都放到后台线程，结果缓存起来，tick 只读缓存。

### 11.6 流水线

每一秒的数据按固定顺序经过几个步骤，每一步只做一件事：

```
tick():
    clashSample = clash.poll()；systemSample = system.poll()
    deltas = reconciler.merge(clashSample, systemSample, 系统代理端口)   // 对账
    for d in deltas:
        store.add_delta(d)                                            // 按天记账
        累加实时速度
    通知观察者 → snapshot(range) 按时间范围汇总给界面                   // 快照
```

### 11.7 账本与冲正分录（对账的核心）

**问题**：系统流量准确但不知道走没走代理；Clash 知道走没走代理，但会晚到一两秒，还可能漏掉短连接。

**做法**：借用会计记账。每个进程一本账：系统流量一到就先按直连记总量；Clash 晚到说明其中有代理流量时，不改已经记下的账，而是追加一笔「负的直连」，把字节挪到代理名下，相当于冲正。

伪代码：

```
class Ledger:
    etw累计, clash累计, clash代理累计, 已记总量, 已记代理

    step(本秒系统流量, 本秒Clash连接):
        etw累计 += 本秒系统流量
        clash累计 += Clash连接的字节
        clash代理累计 += 其中走代理的字节

        目标总量 = etw累计
        if 系统流量已经连续 5 秒没出现:          // 宽限期过了，系统流量看不到这些字节
            目标总量 = max(目标总量, clash累计)    // 按 Clash 补记

        新增 = 目标总量 - 已记总量;  已记总量 = 目标总量

        // 代理比例由 Clash 决定
        目标代理 = 已记总量 × clash代理累计 / clash累计
        代理增量 = 目标代理 - 已记代理;  已记代理 = 目标代理

        return { 新增, 代理增量 }    // 直连 = 新增 - 代理增量，可以是负数（冲正）
```

源码中的关键几行：

```rust
// src-tauri/src/merge.rs —— Ledger::step()
let booked = self.booked_up + self.booked_down;
let clash_total = self.clash_up + self.clash_down;
let target = if self.proxied_by_ratio {
    if clash_total > 0 { ((booked as f64 * self.clash_proxied as f64) / clash_total as f64).round() as i64 } else { 0 }
} else {
    self.clash_proxied.min(booked)
};
let proxied = target - self.booked_proxied;   // 可能让本次「直连」为负，即冲正
self.booked_proxied = target;
```

举例：第 1 秒系统流量报 curl 下载 4000 字节，先全记直连；第 2 秒 Clash 报这 4000 字节都走了代理，于是第 2 秒输出「总量 +0、直连 −4000、代理 +4000」。累计结果正确，每个字节只记一次。

### 11.8 缓冲窗口（类似抖动缓冲）

**问题**：两个数据源到达时间不一致，谁先到都可能。

**做法**：用一个很短的等待窗口让两边对齐。项目里有三处：

| 窗口 | 等什么 | 时长 |
|---|---|---|
| `held`（`TickState`） | 代理还在发现中，暂存系统流量，等知道有没有 Clash 再一起对账 | 直到发现结束 |
| Ledger 宽限期（`GRACE_TICKS`） | Clash 报了、系统流量没看到的字节 | 5 秒 |
| `pending_unknown` / `core_clients` | 未识别进程的代理连接，和最近连过内核的应用互相等 | 3 秒 |

第三个窗口的伪代码：

```
claimUnknownProxy(本秒未识别连接, 本秒经内核的应用):
    所有 coreClients.age += 1
    for 应用 in 本秒经内核的应用（且没有对应的 Clash 连接）:
        coreClients[应用].bytes += 回环字节;  age = 0
    删除 age >= 3 的 coreClients

    待认领 = pendingUnknown + 本秒未识别连接
    if coreClients 为空:
        未识别连接.age += 1
        age >= 3 的 → 记为「未识别进程」（大概率是局域网设备）
        其余继续留在 pendingUnknown
    else:
        按各应用回环字节的比例，把待认领的字节分给 coreClients
        清空 pendingUnknown
```

### 11.9 责任链（降级链）

**问题**：找 Clash 控制接口有多种途径，可信程度不同，而且任何一种都可能失败。

**做法**：按可信程度收集候选，逐个验证，第一个答复的胜出。

```rust
// src-tauri/src/discovery.rs
pub fn discover() -> Option<(Endpoint, String)> {
    let mut candidates: Vec<Endpoint> = vec![];
    // … add() 去重后加入
    for core in platform::list_processes(CORE_NAMES) { add(endpoints_from_core(&core)); }   // 1. 运行中的内核
    add(platform::known_endpoints());                                                       // 2. 已知客户端配置
    add(platform::socket_endpoints());                                                      // 3. 本地 socket 扫描

    for ep in candidates {
        if let Ok(Version { version: Some(v) }) = request::<Version>(&ep, "/version", Duration::from_millis(1500)) {
            return Some((ep, v));
        }
        // 不是控制接口、密钥不对或没在运行：交给下一个
    }
    None
}
```

### 11.10 状态机

`EtwSource` 有几种状态：未启用、等待 UAC、启动中、运行中、出错。状态决定界面显示的文字和按钮。用几个标志位实现，按优先级判断：

```rust
// src-tauri/src/platform/windows/etw.rs
fn status(&self) -> SourceStatus {
    if s.ready      { return mk("on",    "已启用", Some("停用")); }
    if s.prompting  { return mk("off",   "请在管理员授权窗口中确认…", None); }
    if starting(&s) { return mk("off",   "正在启动…", None); }
    if let Some(e) = &s.last_error { return mk("error", e, Some("启用")); }
    if s.enabled    { return mk("error", "采集程序未运行", Some("启用")); }
    mk("off", "未启用：按应用统计全部流量需要管理员授权", Some("启用"))
}
```

```
未启用 ──点「启用」──▶ 等待 UAC ──同意──▶ 启动中 ──收到第一行数据──▶ 运行中
                         │                  │                              │
                       拒绝              超过 15 秒                      6 秒无数据
                         ▼                  ▼                              ▼
                       出错 ◀──────────────┴──────────────────────────────┘
```

macOS 的 `NettopSource` 只有「已停用 / 正在启动 / 运行中 / 出错」四种，同样由 `status()` 按优先级判断。

### 11.11 TTL 缓存与惰性刷新

**问题**：网卡、系统代理这些信息变化很少，每秒执行一次外部命令太浪费。

```rust
// src-tauri/src/platform/macos/sysproxy.rs
const REFRESH: Duration = Duration::from_secs(15);

pub fn system_proxy_ports() -> HashSet<u16> {
    let mut s = STATE.lock().unwrap();
    if s.last_refresh.is_none_or(|t| t.elapsed() > REFRESH) {
        s.last_refresh = Some(Instant::now());
        refresh();                                  // 过期才起一个后台线程去刷新
    }
    s.ports.iter().copied().collect()               // 立即返回缓存值，不阻塞
}
```

进程路径表则是「未命中才刷新」：nettop 里出现不认识的 PID，或者 PID 被复用（进程名对不上）时，才重新执行一次 `ps`。

### 11.15 模块级单例

`settings`、`store`、`collector` 都是一个文件一个实例的模块级状态，首次使用时初始化，没有单例类。Rust 里用 `OnceLock` + `Mutex`：

## 12. 已知限制

- 只统计 AppTraffic 运行期间的流量。
- 「直连 / 代理」的拆分在 TUN 模式下按 Clash 的比例估算，不是逐字节精确。
- 不在内置名单里的 VPN 客户端，外层流量会和应用流量重复计算。
- Windows 上 WireGuard 内核驱动的外层流量可能记在 System 名下。
- macOS 上 Safari 等 WebKit 应用的流量都记在 `com.apple.WebKit.Networking` 名下，而且只有对端 IP，没有域名（nettop 不提供 DNS 信息）。
- TUN 模式和真实 VPN 场景目前只有离线测试，还没有实机验证。
- Windows 依赖系统的 WebView2（Windows 10/11 已自带，较旧系统需要装运行时）。
- 迁移到 Tauri 后弹窗的位置、高度自适应和失焦隐藏，只在 Windows 上用过；Mac 上的菜单栏图标和弹窗位置还需要肉眼确认。
- 安装包 / dmg 没有代码签名。
