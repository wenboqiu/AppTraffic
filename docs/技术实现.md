# AppTraffic 技术实现

AppTraffic 是一个托盘（菜单栏）常驻工具，按应用统计上网流量，并区分直连、经代理、经 VPN 三条路线。本文介绍它用到的技术，以及各部分是怎么配合的。

## 1. 技术栈总览

| 层 | 技术 | 作用 |
|---|---|---|
| 应用框架 | Electron 31 + TypeScript 5 | 托盘程序、弹窗、主进程逻辑 |
| 构建 | electron-vite（Vite 5） | 分别打包主进程、preload、渲染进程 |
| 界面 | React 18 | 弹窗里的统计界面 |
| Windows 流量采集 | Rust（ferrisetw + windows-sys） | 管理员权限的 ETW 助手 `traffic-etw.exe` |
| macOS 流量采集 | 系统自带 `nettop` | 普通权限，按进程、按连接输出字节数 |
| 代理信息 | Clash 兼容 REST API | 每条连接走了哪个节点、目标域名 |
| 打包 | electron-builder | Windows NSIS 安装包；macOS dmg（x64 + arm64） |

代码约 3500 行（不含界面），其中 Rust 助手约 800 行。

## 2. 整体结构

```
                  ┌───────────────────────── 主进程（Node.js）─────────────────────────┐
                  │                                                                      │
 traffic-etw.exe ─┼─▶ 系统流量源 ──┐                                                     │
 (命名管道, JSON)  │  (Windows)     │                                                     │
                  │                ├─▶ collector（每秒一次）─▶ merge 对账 ─▶ store 按天记账 ─┼─▶ traffic.json
 nettop ──────────┼─▶ 系统流量源 ──┤                                         │            │
 (标准输出, CSV)   │  (macOS)       │                                         ▼            │
                  │                │                                   快照（IPC）         │
 Clash API ───────┼─▶ 代理流量源 ──┘                                         │            │
 (socket / HTTP)  │                                                          │            │
                  └──────────────────────────────────────────────────────────┼────────────┘
                                                                             ▼
                                                              渲染进程（React 弹窗）
```

主要目录：

- `native/`：Rust 写的 Windows ETW 助手
- `src/main/services/`：与平台无关的核心逻辑（采集调度、对账、存储、代理发现）
- `src/main/platform/`：平台相关部分，`win32/` 和 `darwin/` 各实现一份 `Platform` 接口
- `src/renderer/`：界面
- `src/shared/`：主进程和界面共用的类型与格式化函数

## 3. 系统流量采集

两个平台的采集方式完全不同，但都输出同一种数据结构 `SystemSample`：

- `procs`：每个进程的上网字节数（按网卡拆分）和对端主机
- `loops`：本机回环连接，即「谁连了本机哪个进程的哪个端口」，用来识别「应用 → 本地代理」
- `ifaces`：涉及到的网卡，以及是否判定为 VPN

### 3.1 Windows：ETW + Rust 助手

ETW（Event Tracing for Windows）是 Windows 内核的事件追踪机制，能拿到每个 TCP/UDP 收发事件以及发起它的进程，但需要管理员权限。所以采集放在一个独立的 Rust 程序 `traffic-etw.exe` 里，用 `ferrisetw` 库订阅三个事件源：

| 事件源 | 用途 |
|---|---|
| Microsoft-Windows-Kernel-Network | TCP/UDP 收发事件：进程 ID、字节数、本地和远端地址 |
| Microsoft-Windows-DNS-Client | DNS 查询结果（事件 3008），把 IP 还原成域名 |
| Microsoft-Windows-Kernel-Process | 进程启动事件，记下 exe 路径 |

几个实现要点：

- **进程归属**：用事件里的 PID 字段，不用事件头里的 PID（收包事件的事件头 PID 常常是 4，即 System）。
- **方向**：TCP 事件里 saddr 总是本机、daddr 总是远端，不分收发；UDP 事件则按实际包方向。
- **短命进程**：ETW 事件有约 1 秒的缓冲延迟，进程可能在事件到达前就退出了，事后查不到 exe 路径。所以在进程启动时就把路径记下来。事件里是 `\Device\HarddiskVolume3\...` 这样的 NT 设备路径，用 `QueryDosDeviceW` 转成盘符路径。受保护进程打不开的，退回用 Toolhelp 快照取进程名。
- **回环流量**：目标是 127.0.0.1 / ::1 的连接不算上网流量，用 `GetExtendedTcpTable` 查出监听这个端口的进程，作为一条 `loop` 上报。
- **网卡**：用 `GetAdaptersAddresses` 按本机地址判断流量走的哪块网卡，每 10 秒刷新一次。IfType 为隧道 / 虚拟类型，或名字里带 VPN 相关关键词的，判定为 VPN；Hyper-V、VMware、VirtualBox、蓝牙、WAN Miniport 等排除在外。
- **传输**：每秒把增量序列化成一行 JSON，通过命名管道 `\\.\pipe\apptraffic-etw` 发给托盘程序。管道的安全描述符只允许 SYSTEM、管理员和交互式登录用户访问。托盘程序断开 30 秒后助手自行退出。

**免 UAC 启动**：第一次启用时弹一次 UAC，由 PowerShell 脚本 `etw-task.ps1` 注册计划任务 `\AppTraffic\ETW Collector`，设置为最高权限运行，并授权当前用户启动它。之后每次打开 AppTraffic，用 `schtasks /Run` 静默拉起助手。为了防止权限被滥用，计划任务只会指向 Program Files 下的 `traffic-etw.exe`，这个位置普通用户无法替换文件；装在其他位置时，退回为每次启用都弹 UAC。

### 3.2 macOS：nettop

macOS 自带的 `nettop` 普通权限就能看到所有进程的流量。AppTraffic 常驻一个子进程：

```
nettop -L 0 -s 1 -d -x -n -J interface,state,bytes_in,bytes_out
```

每秒输出一段 CSV：先是进程行（`名字.PID`，以及这一秒的收发字节），下面跟着它当前的每条连接（协议、地址、网卡、状态、字节数）。

几个实现要点：

- **增量**：`-d` 输出差值，但第一段是各进程启动以来的累计值，要丢掉。
- **进程路径**：nettop 里的进程名会被截断到约 15 个字符，所以按 PID 用 `ps -axo pid=,comm=` 查完整路径。遇到不认识的 PID，或者 PID 被复用（进程名对不上）时，重新读一次进程表。
- **回环流量**：`lo0` 上远端端口是另一个进程监听端口的连接，记为 `loop`。监听端口来自 nettop 自己输出的 `Listen` 状态连接。
- **已关闭的连接**：进程行的字节数包括这一秒内已经关掉的连接，但这些连接没有明细行。差额按这个进程上一次可见的连接构成（回环 / 各网卡的比例）分摊。都没有的，记到默认路由网卡上。
- **网卡与 VPN**：用 `ifconfig` 取网卡地址，`route -n get default` 取默认网卡，每 10 秒刷新。有可路由地址的 `utun` / `ppp` / `ipsec` 网卡算 VPN；macOS 自己会挂几个只有 fe80 地址的空闲 utun，这些排除。只连着一个 VPN 服务时，用 `scutil --nc list` 里的服务名作为显示名。地址在 198.18.0.0/15 的是 Clash 的 TUN，不算 VPN。
- **应用名**：macOS 应用常把联网放在子进程里，比如 `Google Chrome Helper`。凡是在 `.app` 包里的进程，都归到包名下。代理内核和 VPN 客户端除外，它们要靠自己的进程名识别。

## 4. 代理信息：Clash 兼容 API

系统流量只知道「这个应用收发了多少字节」，不知道哪些走了代理。mihomo（Clash Meta）、sing-box 等代理内核提供一套 REST API，`/connections` 里列出每条连接的进程、目标域名和代理链路。AppTraffic 每秒轮询一次，按连接 ID 计算差值。

### 4.1 自动发现

用户不用填任何配置，按可信程度依次尝试：

1. **正在运行的内核进程**：按进程名（verge-mihomo、mihomo、clash-meta、sing-box 等）找到内核。从命令行参数里读出配置文件路径（mihomo 的 `-d` / `-f`，sing-box 的 `-c` / `-D`），有时控制接口本身也在命令行上（`-ext-ctl`、`-ext-ctl-pipe`、`-ext-ctl-unix`、`-secret`）。再从配置里读 `external-controller`、`external-controller-pipe` / `-unix`、`secret`；sing-box 读 JSON 里的 `experimental.clash_api`。父进程名用来标出客户端，比如 clash-verge 对应「Clash Verge」。
   - Windows 用 PowerShell 的 `Get-CimInstance Win32_Process` 读进程列表和命令行。
   - macOS 用 `ps`。`ps` 输出的命令行会丢掉引号，路径里有空格时分不清参数边界，所以按「`-参数名 值`」的规律切分。
2. **已知客户端的配置位置**：比如 Clash Verge 的配置目录，用于内核以服务或其他用户身份运行、读不到命令行的情况。
3. **本地 socket 扫描**：Windows 的命名管道 `\\.\pipe\*`，macOS 的 `/tmp`、`/tmp/verge` 下的 `.sock` 文件。

每个候选都用 `GET /version` 确认能连通。连不上时每 10 秒重新发现一次。

### 4.2 连接分类

每条 Clash 连接按进入内核的方式分类，这决定了它和系统流量怎么对账：

| 类别 | 含义 | 系统流量里能看到什么 |
|---|---|---|
| proxy | 应用连本机 HTTP/SOCKS 代理端口 | 应用 → 内核端口的回环流量 |
| tun | 被 TUN 网卡接管 | 应用自己名下的流量 |
| inner | 内核自己发起的（DNS、规则更新等） | 内核名下 |
| gap | 内核总计数里，轮询没捕捉到的短连接 | — |

TUN 模式下还会读 `/configs` 拿到 TUN 网卡名（缓存 30 秒），避免把 Clash 自己的 TUN 网卡当成 VPN。

## 5. 对账（merge.ts）

这是整个项目最核心的部分：系统流量和 Clash 各看到一部分事实，要合成「每个应用、每条路线各多少字节」，而且每个字节只记一次。

**基本原则：系统流量定总量，Clash 定比例。** 系统流量是内核级计数，不会漏；Clash 知道哪些连接走了代理、哪些直连，但轮询有间隔，短连接可能漏掉。

- **Ledger（每个进程两本账）**：一本记应用自己的出网流量，一本记应用经内核端口的流量。系统流量到了就记总量；Clash 的数据可能晚到一两秒，晚到的代理部分用负的「直连」修正，把已经记成直连的字节挪到代理名下。
- **宽限期**：Clash 报了而系统流量一直没看到的字节，等 5 秒再按 Clash 补记，避免两边时间差造成重复。
- **系统代理模式**：应用经代理的量取「应用 → 内核端口」的回环字节；内核自己的出网流量不再算给任何应用，否则会重复。
- **进程识别关闭时**：Clash 的 `find-process-mode: off` 时，代理连接不带进程名。这时把这部分流量按回环流量的比例，分给最近 3 秒内连过内核端口、又没有对应 Clash 连接的本机应用。两边都等对方最多 3 秒。没有这样的应用时，判定为局域网设备经本机代理（allow-lan），记为「未识别」。
- **没有 API 的本地代理**（如 xray）：按各应用连到系统代理端口的回环流量，比例分摊代理进程的出网流量。系统代理端口在 Windows 上读注册表 Internet Settings，在 macOS 上读 `scutil --proxy`。
- **VPN**：流量走 VPN 网卡的，记为「VPN · 网卡名」路线。VPN 客户端进程自己的加密外层流量（内置一份客户端名单，如 openvpn、wireguard、tailscaled 等）记为「隧道」，不计入总量和网速，因为它和应用流量是同一份字节。

对账逻辑有 26 个离线测试场景，覆盖系统代理、TUN、两边时间差、局域网设备、无 API 代理、WireGuard、Clash 和 VPN 同时使用等情况。

## 6. 存储

- 文件：Electron 的 userData 目录下的 `traffic.json`
  - Windows：`%APPDATA%\app-traffic\`
  - macOS：`~/Library/Application Support/app-traffic/`
- 结构：`日期 → 进程 → { 上传, 下载, 各路线字节数, exe 路径, 访问最多的主机 }`。路线是一个 key → 字节数的表：`direct`（直连）、`tunnel`（隧道）、代理客户端名、`VPN · 网卡名`。
- 保留 90 天，内存中累计，每 30 秒和退出时写盘。先写临时文件再重命名，避免写到一半损坏。
- 版本迁移：数据格式从 v1（只有「经 Clash / 直连」）升级到 v2（任意路线）时，自动转换并保留 `.v1.bak` 备份。首次运行会复制前身 ClashTraffic 的历史数据，原文件不动。

## 7. 界面

- 托盘图标常驻，点击弹出无边框窗口，窗口位置按托盘所在的屏幕边缘计算（Windows 任务栏在下，macOS 菜单栏在上）。
- 弹窗始终保持渲染，只是透明并且鼠标穿透，所以每次打开都不闪。渲染进程上报内容高度，主进程据此调整窗口大小。
- 主进程每秒推送一次快照（IPC），包括各数据源的状态、总量、各路线合计、按进程的排行和实时速度。
- macOS 上隐藏 Dock 图标（打包时设置 `LSUIElement`）。托盘左键打开弹窗，右键打开菜单。
- 设置（是否启用系统流量）存在 userData 下的 `settings.json`。

## 8. 打包与发布

| 平台 | 产物 | 要点 |
|---|---|---|
| Windows | NSIS 安装包（x64） | 安装到 Program Files（perMachine），保证计划任务指向的助手不能被普通用户替换。安装、卸载时先结束助手进程；卸载（非升级）时删除计划任务 |
| macOS | dmg（x64 + arm64） | 没有原生依赖，Intel Mac 上就能打出两个架构。打包后删掉 Electron 框架里中英文以外的语言包，并重新做 ad-hoc 签名（Apple 芯片必须有签名才能运行）。没有开发者证书，第一次打开需要右键「打开」 |

- 两个平台都只保留中文和英文语言包，安装包分别约 72 MB（Windows）、85–93 MB（macOS），大头是 Electron 自带的 Chromium。
- 打包产物按版本号收集到 `dist/<版本号>/`，中间文件放在 `dist/.build/`。

## 9. 已知限制

- 只统计 AppTraffic 运行期间的流量。
- 「直连 / 代理」的拆分在 TUN 模式下按 Clash 的比例估算，不是逐字节精确。
- 不在内置名单里的 VPN 客户端，外层流量会和应用流量重复计算。
- Windows 上 WireGuard 内核驱动的外层流量可能记在 System 名下。
- macOS 上 Safari 等 WebKit 应用的流量都记在 `com.apple.WebKit.Networking` 名下，而且只有对端 IP，没有域名（nettop 不提供 DNS 信息）。
- TUN 模式和真实 VPN 场景目前只有离线测试，还没有实机验证。
